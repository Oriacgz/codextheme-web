# codexskin Community

A community theme library for codexskin. Browse theme previews, share packages, download themes and discuss them with other users.

Built with React, Vite, Tailwind CSS and Motion, with a Node.js API, Prisma and PostgreSQL. The frontend and backend are independent npm projects hosted on Vercel (frontend) and Render (backend).

## Features

- Searchable community collection with previews rendered from saved theme settings.
- Validated ZIP and `.codextheme` uploads, immediate publication and original-file downloads.
- Accounts, profiles, a 6 × 4 shuffleable Blobatar picker and interactive avatars.
- Likes, dislikes and comments, with server-enforced administration and moderation.
- Uploaders can permanently delete their themes from collection/profile cards or the detail page, with confirmation. Deletion removes files, reactions and comments.
- Optimistic reactions, bounded preview caching and independently loaded pages.

## Project structure

```text
front-end/               React pages, components, services, styles and public assets
back-end/src/            Authentication, API, database, storage and theme validation
back-end/prisma/         Database schema and versioned migrations
back-end/scripts/        Database, administration and maintenance commands
back-end/test/           Automated tests and fixtures
back-end/.env.example    Server configuration template
front-end/api/community.js Vercel proxy to Render
docs/                   Architecture, package specification and audit findings
front-end/package.json  Frontend commands
back-end/package.json   Backend commands
front-end/vercel.json   Deployment and security-header configuration
```

Run frontend commands from `front-end` and backend commands from `back-end`. Each has its own package manifest and lockfile. Select the corresponding folder as each service’s Root Directory. The local development server forwards `/api/community` to the same handler used in production.

## Local development

Use Node.js 24 and npm.

```sh
cd back-end
npm ci --include=dev
npm run db:generate
npm run db:local
```

Keep the database process running. Create `back-end/.env.local` from `back-end/.env.example`, using the local PostgreSQL URL printed by the database command. Set `APP_ORIGIN` to `http://127.0.0.1:5173` and generate a session secret:

```sh
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Leave `BLOB_READ_WRITE_TOKEN` empty for local filesystem storage. In another terminal:

```sh
cd back-end
npm run db:migrate
cd ../front-end
npm ci
npm run dev
```

Open `http://127.0.0.1:5173`. Local uploads are stored in `back-end/.data/uploads/`. No themes or administrator accounts are seeded. Use a local database for testing; never run integration tests against production.

## Deployment: Vercel frontend and Render backend

The browser calls `/api/community` on the frontend domain. A small Vercel proxy forwards requests to Render, including origin, session cookies and CSRF headers. This keeps browser authentication same-origin; no public frontend API secret or cross-site cookie configuration is needed. Local Vite development still calls the backend handler directly.

### Render web service

Create a Render Node.js web service with Root Directory `back-end` and Node.js 24.

| Setting           | Value                                         |
| ----------------- | --------------------------------------------- |
| Build command     | `npm ci --include=dev && npm run db:generate` |
| Start command     | `npm start`                                   |
| Health check path | `/health`                                     |

The server binds to `0.0.0.0` and Render's supplied `PORT`. Apply `npm run db:migrate` against the intended database before using the service. The build does not apply migrations automatically.

Set these environment variables on **Render**:

| Variable                | Value                                                                |
| ----------------------- | -------------------------------------------------------------------- |
| `NODE_ENV`              | `production`                                                         |
| `DATABASE_URL`          | Native PostgreSQL connection URL                                     |
| `APP_ORIGIN`            | Exact Vercel frontend origin, e.g. `https://your-project.vercel.app` |
| `SESSION_SECRET`        | Random secret generated by the command in Local development          |
| `BLOB_READ_WRITE_TOKEN` | Secret token for a private Vercel Blob store                         |

The existing `codexthemelibrary_POSTGRES_URL` can replace `DATABASE_URL`; the prefixed `codexthemelibrary_DATABASE_URL` is also supported. `DATABASE_URL` takes precedence. Copy the selected native database connection value privately to Render; a Vercel integration does not automatically configure Render.

PostgreSQL stores accounts and theme metadata. Private Vercel Blob stores uploaded packages and preview images. Its token allows Render to read/write those files. Create a private store on Vercel and configure its token on Render; production filesystem storage is intentionally disabled. The database and file storage can stay on Vercel even though the API runs on Render.

`APP_ORIGIN` must match the frontend domain visitors use, including `https://`, without a trailing slash or path. Preview environments need their own exact origin and preferably separate data/storage. No wildcard origin is accepted. Render supplies `PORT`; do not set `VERCEL` on Render.

### Vercel frontend

Select `front-end` as the Vercel Root Directory. Use framework Vite, Node.js 24, install command `npm ci --workspaces=false`, build command `npm run build` and output directory `dist`. Leave the option to include files outside the Root Directory disabled. The frontend has its own package manifest, lockfile, Vercel configuration and API proxy; its production build does not import the backend or require Prisma generation.

Set only this application variable on **Vercel**:

| Variable      | Value                                                     |
| ------------- | --------------------------------------------------------- |
| `BACKEND_URL` | Render HTTPS origin, e.g. `https://your-api.onrender.com` |

Use the backend origin only, without a path. It is read by the server-side proxy, not exposed through `VITE_`. The Vercel build does not need database, session or Blob credentials. The frontend API proxy has a 55-second upstream timeout and returns a retryable message if Render is unavailable.

Redeploy after changing environment variables. Keep credentials out of Git and browser code. See [Render web services](https://render.com/docs/web-services), [Vercel environment variables](https://vercel.com/docs/environment-variables) and [private Blob storage](https://vercel.com/docs/vercel-blob/private-storage).

### Administrator and deployment verification

Sign up on the frontend, then run this command with the production database privately configured:

```sh
npm run admin -- your-email@example.com
```

There is no default administrator, automatic first-user promotion or administrator environment variable. Verify signup, login, uploads, preview/download access and moderation after both services are deployed. Infrastructure quotas and service cold starts can affect availability and latency.

## Verification and maintenance

```sh
cd back-end
npm test
npm run test:integration
npm audit
cd ../front-end
npm run build
npm audit
```

Integration tests require a migrated local database and local storage. They create disposable records, verify permissions and publishing flows, and remove their fixtures. Cloud database hosts and Blob storage are rejected by the test script.

Run `npm run maintenance` from `back-end` periodically with the intended database and storage configuration to remove expired sessions, rate buckets and unpublished uploads. Upload cleanup processes up to 100 pending records per run and preserves published themes.

See the [architecture](docs/ARCHITECTURE.md), [package format](docs/PACKAGE-FORMAT.md) and [audit findings](docs/AUDIT-2026-10-04.md).

## Security and compatibility

Uploads are bounded ZIP packages containing codexskin metadata and PNG, JPEG or WebP artwork. The server checks paths, sizes, expansion, checksums, metadata and decoded image bounds. It does not execute uploaded content. Custom CSS and foreign package layouts are rejected. Downloaded packages retain their original bytes.

Passwords use salted scrypt. Session tokens are hashed in storage; cookies are HttpOnly and Secure on Vercel. Origin/CSRF checks and administrator permissions are enforced by the server. Preview caching preserves access checks for hidden themes.

Previews approximate the desktop layout from saved palette, text, opacity, darkness, brightness and image-position settings using resized artwork. Cold starts and database/storage latency can still affect response times. Email verification, password recovery and MFA are not implemented. Comment and administrative views currently show the latest 50 entries.
